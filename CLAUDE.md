# CLAUDE.md — Fast Feature Development (Existing Codebase)

> **This codebase already exists.** You are adding to it, not building from scratch.
> Your job: understand what's here → plan the change → execute → verify → commit.
> No greenfield ceremonies. No sprint theater. Just ship features fast and correctly.

## Cardinal Rules

1. **READ BEFORE YOU WRITE** — Grep the codebase for existing patterns before creating anything new. Most features are variations on what already exists.
2. **PLAN EVERY CHANGE** — Never code without a written plan, even for "quick" fixes. Plans catch mistakes that cost 3-5x more to fix after the fact.
3. **NEVER REPEAT A MISTAKE** — Check MEMORY.md before starting. Log every lesson after hitting one. Same mistake twice is unacceptable.
4. **MATCH EXISTING PATTERNS** — This codebase has conventions. Find them, follow them. Don't invent new patterns when existing ones work.
5. **ONE PROMPT, COMPLETE RESULT** — The user shouldn't need to follow up. If something is unclear, ask everything in ONE message before starting.

## 1. Feature Development Workflow

This is your core loop. Every feature follows this.

### Step 1: Understand (before touching anything)

```
Read the relevant code FIRST. Always.
```

Before planning or coding:
1. **Grep for similar patterns** — `grep -r "similar feature" src/` to find how it was done before
2. **Read 1-2 reference files** — Find the closest existing feature and study its structure
3. **Check MEMORY.md** — Any past lessons relevant to this area?
4. **Identify the blast radius** — Which files will change? What could break?

For a new settings page, don't design from scratch. Find the existing settings pages. Read them. Your new one should look like those.

### Step 2: Plan (written, not mental)

Write a `plan.md` in the chat or in `.planning/` for anything touching 2+ files:

```markdown
## Feature: [Name]
**Goal**: [One sentence — what does "done" look like?]
**Reference**: [Existing file(s) this should follow the pattern of]

**Changes**:
1. `src/app/api/settings/route.ts` — Add PATCH endpoint for user preferences
2. `src/features/settings/PreferencesForm.tsx` — New form component (follow `ProfileForm.tsx` pattern)
3. `src/stores/settings.ts` — Add preferences slice
4. `src/__tests__/settings.test.ts` — Integration test for PATCH endpoint

**Edge cases**: Empty state, validation errors, unauthorized access
**Verify**: `curl -X PATCH localhost:3000/api/settings` returns 200
```

**Key insight**: Point to reference files. "Follow the pattern in `ProfileForm.tsx`" communicates all implicit requirements without spelling them out.

### Step 3: Execute (match patterns, commit atomically)

- Follow existing patterns exactly — naming, folder structure, imports, error handling
- One logical change = one atomic commit with conventional message
- Run `<verify>` step after each change
- If something goes wrong: **revert and re-scope**, don't patch a bad approach

### Step 4: Verify

- Run relevant tests
- Build passes
- Manual spot-check if UI is involved
- No regressions in related features

## 3. Subagent Strategy (Keep Main Context Clean)

The main conversation coordinates. Subagents do the heavy lifting.

## 4. Pattern Matching (The Brownfield Superpower)

**Most features in a mature codebase are variations on existing patterns.** Use this.

### Before Creating Anything New

```bash
# Find how similar features were built
grep -r "createUser\|createPost\|createOrder" src/ --include="*.ts" -l

# Find the component pattern
ls src/features/*/components/

# Find the API route pattern
ls src/app/api/*/route.ts

# Find the test pattern
find src -name "*.test.ts" -path "*__tests__*" | head -5
```

### Pattern Reference Prompting

Instead of describing what you want from scratch, point to existing code:

**Bad**: "Create a new API endpoint for user preferences with validation, error handling, and proper types"

**Good**: "Create a PATCH endpoint at `src/app/api/preferences/route.ts` following the same pattern as `src/app/api/profile/route.ts`. Same validation style, same error response shape, same auth middleware."

This communicates 90% of the requirements implicitly. Claude reads the reference file and matches it.

### When You Find a Pattern Mismatch

If the codebase has inconsistent patterns (it will), document the canonical one:

```markdown
<!-- Add to this CLAUDE.md under Project section -->
- **Canonical patterns**:
  - API routes: Follow `src/app/api/profile/route.ts` (NOT `src/app/api/legacy-users/route.ts`)
  - Forms: Follow `src/features/settings/ProfileForm.tsx` (NOT the old `src/components/forms/` pattern)
  - Store: Follow `src/stores/auth.ts` pattern for new Zustand stores
```

## 5. UI/UX Design Intelligence (ui-ux-pro-max)

**Install the skill**: `npm install -g uipro-cli && uipro init --ai claude`

This gives Claude access to 67 UI styles, 96 color palettes, 57 font pairings, 99 UX guidelines, and 100 industry-specific reasoning rules. The skill auto-activates on any UI/UX task.

### Design System First, Code Second

Before building ANY UI feature, generate or reference a design system:

```bash
# Generate a design system for your project (run once, persist across sessions)
python3 .claude/skills/ui-ux-pro-max/scripts/search.py "your product type" --design-system --persist -p "YourApp"

# Page-specific overrides (when a page deviates from master)
python3 .claude/skills/ui-ux-pro-max/scripts/search.py "dashboard analytics" --design-system --persist -p "YourApp" --page "dashboard"
```

This creates a hierarchical design system:

```
design-system/
├── MASTER.md           # Global: colors, typography, spacing, components
└── pages/
    ├── dashboard.md    # Dashboard-specific overrides
    └── settings.md     # Settings page overrides
```

### Design System Retrieval (Every UI Task)

Before writing any UI code, load the design system:

```
1. Read design-system/MASTER.md (global rules)
2. Check if design-system/pages/{page-name}.md exists
3. If page file exists → its rules OVERRIDE the Master
4. If not → use Master exclusively
5. Then implement following the design system
```

### UI/UX Rules (Non-Negotiable)

These apply to EVERY UI component you create:

**Interactions**:
- `cursor-pointer` on ALL clickable elements — no exceptions
- Hover states with smooth transitions (150-300ms ease)
- Focus states visible for keyboard navigation (2px solid outline)
- `prefers-reduced-motion` respected — wrap animations in media query
- Touch targets minimum 44x44px on mobile

**Visual Quality**:
- NO emojis as icons — use SVG icon libraries (Lucide, Heroicons)
- Light mode text contrast minimum 4.5:1 (WCAG AA)
- Dark mode text contrast minimum 4.5:1
- Consistent spacing scale (4px base: 4, 8, 12, 16, 24, 32, 48, 64)
- No orphaned text (single words on their own line)

**Responsive**:
- Test at breakpoints: 375px, 768px, 1024px, 1440px
- Mobile-first approach — base styles for mobile, enhance with `min-width`
- No horizontal scroll on any breakpoint
- Images and media with proper aspect ratios and `object-fit`

**Performance**:
- Lazy load images below the fold
- Use `next/image` or equivalent optimized image component
- Font loading with `display: swap` to prevent FOIT
- Skeleton loaders for async content (not spinners for primary content)

**Anti-Patterns to AVOID**:
- Generic AI aesthetics (purple/pink gradients on everything)
- Neon colors on business/enterprise products
- Dark mode as default for non-technical audiences
- Animations longer than 300ms for UI transitions
- Modal dialogs for non-critical information
- Infinite scroll without "back to top" and URL state preservation
- Placeholder text as labels (use floating labels instead)
- Disabling the submit button without explaining why

### Pre-Delivery Checklist (Run Before Every UI Commit)

Before committing ANY UI change, verify:

```
[ ] No emojis used as icons (SVG only: Lucide/Heroicons)
[ ] cursor-pointer on all clickable elements
[ ] Hover states with smooth transitions (150-300ms)
[ ] Focus states visible for keyboard nav
[ ] Text contrast 4.5:1 minimum (both modes)
[ ] prefers-reduced-motion respected
[ ] Responsive: tested at 375px, 768px, 1024px, 1440px
[ ] Loading states present for async operations
[ ] Empty states handled (not blank screens)
[ ] Error states handled with actionable messages
[ ] Design system colors/typography/spacing followed
```

## 8. Context Hygiene

### Forbidden Directories (Never Read)

```
node_modules/  .next/  dist/  build/  coverage/  .git/  *.lock  *.map
```

### Keep Context Lean

- `/clear` between unrelated tasks — stale context wastes tokens every message
- `/compact` after completing a feature before starting the next
- `/cost` to check spend
- Pass file PATHS to subagents, not file contents
- Read ONE reference file to understand a pattern, not all of them
- Delegate test suite runs and large file reads to haiku subagents

### MCP Hygiene

- Disable unused MCP servers (`/mcp`)
- Prefer CLI tools over MCP when available (`gh`, `aws`, `vercel`)
- Check context usage with `/context`

```

```

Narrowing scope after a revert almost always produces better results than incremental fixes on a broken approach.

## 11. Anti-Patterns

| Don't Do This | Do This Instead |
|---------------|-----------------|
| Design from scratch when a pattern exists | Grep → find reference → "follow this pattern" |
| Code without reading existing patterns first | Always `grep` and read 1-2 reference files |
| Code without a plan (even "quick" fixes) | 2-3 sentence plan minimum, always |
| Ask multiple clarifying questions | Batch ALL questions in ONE message |
| Patch a failing approach | Revert, narrow scope, restart |
| Read entire directories into context | `Glob` → `Grep` → read specific files only |
| Use Opus for routine implementation | Sonnet for 80% of work, haiku for subagents |
| Keep stale context between tasks | `/clear` between tasks, `/compact` at breakpoints |
| Let test output fill main context | Delegate test runs to haiku subagent |
| Invent new conventions | Match what exists, document canonical patterns |
| Skip verification | Every change verified before commit |
| Ignore a mistake and move on | Log it to MEMORY.md immediately |
| Use emojis as icons | SVG icons only (Lucide, Heroicons) |
| Ship UI without checking responsiveness | Test 375px, 768px, 1024px, 1440px |
| Skip hover/focus states | Every clickable element needs both |
| Ignore design system, freestyle colors | Read MASTER.md before any UI work |
| Build UI without loading/empty/error states | Handle all three for every async component |

## 12. Session Workflow

### Starting a Feature

```
1. Read CLAUDE.md (auto)
2. Read MEMORY.md — lessons for this area?
3. Scout: grep for existing patterns related to the feature
4. Plan: write changes list with reference files
5. User approves plan (for 3+ file changes)
6. Execute: implement following patterns, commit atomically
7. Verify: tests pass, build passes, no regressions
```

### Resuming Work

```
1. Read CLAUDE.md (auto)
2. `git status` + `git log --oneline -5` — where did you leave off?
3. Check MEMORY.md for any notes from last session
4. Continue from last checkpoint
```

### Ending a Session

```
1. Verify all changes (tests, build)
2. Log any lessons to MEMORY.md
3. If mid-feature: note current state in a commit message or STATE.md
```
